# AiRA workout session architecture

The harness owns transport lifecycle in `Conversation`, declarative screen data in `ScreenDocument`, generic navigation in `createRunNav`, and timer clocks in `TimerLedger`. Workout semantics live in the canonical controller and the authored session policy described below. The generic mock wiring fixture remains separate.

## Architecture and ownership

`src/shared/workout/state.ts` defines the canonical immutable `WorkoutState` and its runtime validation. Duration and elapsed time use integer seconds, with a 3600-second limit matching the existing timer validator. Difficulty is easy, moderate or challenging. Progress is the current phase's simulated elapsed/duration ratio (0–1), not overall screen progress or physical completion. Untimed phases have no movement or duration; complete has progress 1. Paused and elapsed time live here too so future input adapters cannot maintain conflicting copies.

`src/shared/workout/controller.ts` owns state through validated, data-only actions. It exposes immutable snapshots and increasing revisions, validates phase transitions atomically, and derives progress. Reaching a timer's end never advances the phase automatically. Trusted application policy decides transitions. Reset invalidates captured revisions even when already at intro. Asynchronous adapters must capture a revision before work and supply it when dispatching; stale actions return false.

The graph is intro → checkin → warmup → active → recovery → complete. Warmup, active and recovery can enter adaptation; adaptation can return to warmup, active or recovery. Recovery can begin another active interval, and active can complete after the final block. Same-phase transitions and transitions from complete are rejected; reset begins a new run. Timed transitions require a movement label and positive duration. Adaptation changes difficulty or the current timed duration, preserving elapsed time and clamping it when shortened. Untimed adaptation/checkin accept difficulty changes with duration zero; the subsequent timed transition supplies its duration explicitly.

`Conversation` owns one `WorkoutController` per run and resets it with conversation/screens. Its existing request cancellation, retry, provider selection and response validation stay intact. Provider switching preserves workout state. Live text sends a JSON workout snapshot as a data-only client event using the existing transport contract. Accepted ordinary reply text can update the coach cue only at the captured workout revision. Model screens never change the authored session's canonical state.

Text interaction and optional realtime voice adapters share validated actions and snapshots. Neither adapter owns a workout clock, phase graph or animation state. `WorkoutSession.tick()` translates its selected TimerLedger entry into whole elapsed seconds; session policy advances completed timed stages and waits at check-in/adaptation. The browser projects canonical state through registered, validated OpenUI components. Visual animation callbacks never advance phases. Future model-facing components must follow the same registry, prop validation and renderer integration.

## File boundaries

The initial foundation added the shared state/controller and integrated Conversation reset. The authored experience adds `workout/session.ts` for deterministic ten-stage progression using one TimerLedger interval, and `web/session.ts` for the primary surface. Generic OpenUI navigation and fixture timers remain independent.

Three custom components are registered and validated: Trainer(animation, label), Progress(value, label), CoachPanel(cue, phase). The session serializes its snapshot to OpenUI, validates it and uses the trusted renderers. Progress is derived from the authored stage index and canonical phase progress. Trainer animation and pause come from WorkoutState; declarative model props cannot change the workout controller. No model URL is accepted.

`web/trainer.ts` loads the fixed local GLB with Three.js/GLTFLoader, uses AnimationMixer and 0.4-second cross-fades, and disposes animation, geometry, materials, textures, observers and WebGL resources on removal. Reduced motion displays a still pose; WebGL/model failure keeps text and session controls usable. The asset and all eight clips are original, generated by `scripts/create-trainer.mjs`. Libraries are bundled locally by esbuild and the build copies the checked-in asset. The server exposes exactly this GLB path in addition to the existing static roots. Packaging includes the asset.

The primary UI is separate from the original fixture and uses scripted commands in Mock. Recognized local commands also work with a configured live provider. The runtime panel and diagnostic fixture UI are collapsed beneath the session. Voice opens a separate opt-in panel. Its trusted adapter shares the canonical state and authored session policy; it adds no OpenUI components.

## Harness risks and deferred work

- The OpenUI cursor is presentation state. Mapping arbitrary screen indexes to workout phases would corrupt canonical state, especially on Back or document replacement.
- TimerLedger may contain several timers. A later integration must explicitly bind the active workout interval to one timer and coordinate duration changes/reset; no second clock is introduced here.
- Current transport objects reject extra fields. Sending workout snapshots or accepting declarative coaching proposals needs a coordinated schema/protocol change, not an unvalidated side channel.
- Conversation's generation guard protects screen responses. The primary live-text adapter uses a coaching revision that changes on phase, pace, pause, cue or reset actions. Elapsed-only ticks can continue while a reply is pending; accepted cues dispatch at the current general revision only after the coaching revision still matches. This avoids discarding useful replies on every timer tick. Compact JSON snapshot events omit oversized cue/label strings to respect the existing 1000-character event limit.
- Model output stays declarative. The controller is trusted TypeScript, never executable instructions supplied by a model. The authored local command policy accepts a small vocabulary; arbitrary Mock text receives a state-aware hint rather than a claim of model inference.
- OpenUI prompts still prohibit microphone/audio capabilities. Safety lint permits microphone access only in src/web/voice.ts. The optional Realtime adapter uses a separate tool contract, local credentials and explicit usage consent. See VOICE.md.

All actions and test scenarios are synthetic. Existing Mock functionality remains available without credentials. Live provider setup and usage consent requirements are unchanged.
